# JS map engines for choropleth maps (Brazil municipalities and the world)

Scope checked on 2026-10-08. Gzip figures below are `gzip -9` of the exact bytes downloaded that day from the unpkg URL in the same bullet. They are browser-payload sizes, not the npm unpacked package size. “Free/share” here means an OSI-style license (MIT, BSD, Apache, ISC, or equivalent) that lets the caller ship the library inside generated static HTML without paying and without a non-commercial clause. No engine is ranked.

Engines required by the brief are all covered. Two further OSI libraries turned up as current and relevant but were not documented deeply: Apache ECharts and maptalks (see the last question).

### Inferences
- BSD-2-Clause (Leaflet, OpenLayers), BSD-3-Clause (MapLibre), ISC (D3, d3-geo, topojson-client), MIT (deck.gl), and Apache-2.0 (CesiumJS) are the usual permissive grants: shipping a minified copy inside a generated HTML file is allowed if the copyright and license notices travel with it. Apache-2.0 also expects NOTICE-file handling. None of those SPDX names is a non-commercial or “do not compete with the vendor” license. The MIT and Apache license bodies were not re-pasted in this pass; the claim rests on the SPDX identifiers plus, for Cesium, the staff statement that commercial use is allowed.
- Mapbox GL JS 3.32.0 is not free/share under this brief. Redistributing `mapbox-gl.js` inside generated HTML does not by itself create a right to run it: the grant is an account-scoped TOS license for Mapbox products, and it ends when the account ends. That is the restriction analogous to a vendor lock, not an OSI license. Mapbox GL JS 1.13 and earlier remain BSD-3-Clause on paper, but they are the pre-fork line; the maintained open continuation is MapLibre.
- Cesium ion tokens, demo-token replacement, and ion asset quotas attach to the hosted terrain/imagery/geocoder service, not to the Apache-2.0 text of CesiumJS. Using ion is optional paid-or-freemium infrastructure. The library license does not forbid a competing globe.

### Gaps
- The full MIT text for deck.gl and the full Apache-2.0 and ISC texts were not opened in this pass, so notice-placement details (header comments, NOTICE, trademark clauses) are not quoted.
- Highcharts’ current license was not re-read. The comparison above is only that none of the OSI identifiers here is a non-commercial clause, and that Mapbox’s own text is the one that requires the vendor account.
- Current Mapbox or Cesium ion free-tier quotas (requests per month, seat prices) were not retrieved. Only the existence of accounts, tokens, and a limited demo token is sourced.
- Whether Mapbox GL JS 3.32.0 throws at runtime with no `accessToken` when the style is not a Mapbox style was not tested.

## Can each library draw a GeoJSON choropleth with no API key and no tile server?

### Takeaway
Leaflet, OpenLayers, D3 plus topojson-client, and deck.gl can color GeoJSON polygons with no API key, and each has a documented path that does not require a tile server. MapLibre’s quickstart has no API key, but every official GeoJSON example retrieved here still loads a remote style URL. CesiumJS can load GeoJSON or TopoJSON with no ion token if the viewer is pointed away from ion, but a default viewer calls ion. Mapbox GL JS is keyed and account-locked, so it fails the free/share test even though it can paint GeoJSON.

### Inferences
- A choropleth of Brazilian municipalities plus a world country layer does not need a basemap tile server for Leaflet, OpenLayers (vector layer or the geojson-vt example), D3, or deck.gl (`map: false` or no map script). The polygons are the map.
- MapLibre can take an inline GeoJSON source and has no token, but a style document is still required. The official examples satisfy that with a remote style URL, which is a tile server. A background-only style object would avoid tiles; that pattern was not on the pages opened here, so it is not recorded as a verified snippet.
- Cesium can draw the polygons without a key only after ion is switched off. The default viewer is not a no-key, no-tile embedding.
- For TopoJSON, the sourced zero-dependency paths are Cesium’s loader and D3’s `topojson-client` then `d3-geo`. The other engines, on the evidence gathered, want GeoJSON (convert first).

- IBGE municipal GeoJSON was not loaded in any of these libraries in this pass. “Can draw” is from documentation, not from a run against the 5,570-municipality mesh.

## What is the practical polygon count before the browser stalls (SVG vs Canvas vs WebGL)?

### Takeaway
No source retrieved here states a polygon count at which the browser stalls. The best 2025 measurement is initial render time, not interaction collapse: for GeoJSON polygons, Leaflet and OpenLayers were the fastest of the four libraries tested up through 10,000 features, and at 50,000 polygons Mapbox GL JS, OpenLayers, and Leaflet all still finished in roughly 1.3–1.5 seconds while MapLibre was slower. About 5,570 municipality polygons sit inside the band that study treated as the fast case for Leaflet and OpenLayers. That study did not use IBGE meshes, did not include D3, deck.gl, or Cesium, and its MapLibre build is older than 6.13.0 if a secondary summary of the versions is right. Vertex count, not feature count, is unmeasured.

### Cited Findings
- Balla and Gede, ISPRS International Journal of Geo-Information, 2025, DOI 10.3390/ijgi14090336: four libraries, GeoJSON partly extracted from OSM. “Leaflet and OpenLayers excelled for features up to 10,000.” “For up to 50,000 lines and 10,000 polygons, Leaflet and OpenLayers were the fastest in all scenarios.” “For 100,000 lines, OpenLayers was almost twice as fast as the others, while Mapbox rendered 50,000 polygons the quickest.” “The performance of Leaflet and OpenLayers scales with the increasing feature quantities, yet for Mapbox and MapLibre, any performance impact is offset to 1000 features and beyond.” — [MDPI PDF](https://www.mdpi.com/2220-9964/14/9/336/pdf?version=1756544202), [DOI record via scite](https://scite.ai/reports/vector-data-rendering-performance-analysis-zRenRZ4Q)
- The same PDF gives these polygon and line times: 100,000 lines, OpenLayers 1295.5 ms (SD 9.35 ms). 50,000 polygons, Mapbox GL JS average 1265 ms (SD 28.13 ms), OpenLayers 1366.4 ms (SD 11.42 ms), Leaflet 1539.9 ms (SD 25.68 ms). “MapLibre GL JS was significantly slower than all other libraries for both lines and polygons across all scenarios.” The authors note they expected a WebGL advantage and that “their potential edge did not clearly come out.” They call Leaflet and OpenLayers the “HTML canvas-based libraries” in that comparison. A later sentence in the PDF says Leaflet, Mapbox GL JS, and MapLibre took 2594, 2446, and 3579 ms for the 100,000-line case. — [MDPI PDF](https://www.mdpi.com/2220-9964/14/9/336/pdf?version=1756544202)
- The ICA abstract of the same authors (12 Dec 2025, DOI 10.5194/ica-abs-10-14-2025) uses the same means but swaps some standard deviations: Mapbox 50,000 polygons 1265 ms (SD 9.35), OpenLayers 1366.4 ms (SD 28.13), Leaflet 1539.9 ms (SD 25.68). It also says datasets were 50, 100, 500, 1000, 5000, 10000, 50000, 100000 (points and lines only) and 500000 (points only), so the polygon series stops at 50,000. Up to 5,000 points, Leaflet and OpenLayers still led (140 ms and 115.5 ms). — [ICA abstract PDF](https://ica-abs.copernicus.org/articles/10/14/2025/ica-abs-10-14-2025.pdf)
- A secondary write-up dated 2026-10-08 attributes that study’s builds to Leaflet 1.9.4, OpenLayers 10.2.1, Mapbox GL JS 3.7.0, and MapLibre GL JS 4.7.1, and paraphrases “Past 50,000 features every library crossed one second.” Those version pins and the one-second sentence were not visible in the PDF excerpts retrieved here. — [GISCarta, 2026-10-08](https://giscarta.com/blog/mapping-libraries-a-practical-comparison)
- Brazil has on the order of 5,570 municipalities in the brief this note was written for. 5,000 and 10,000 are explicit steps in the ICA dataset list, and the “fastest up through 10,000 polygons” result is the paper’s, not a measurement of IBGE vertices. — [ICA abstract PDF](https://ica-abs.copernicus.org/articles/10/14/2025/ica-abs-10-14-2025.pdf)
- OpenLayers documents `RenderFeature` when “performance is the primary concern” and features will not be edited, and ships a geojson-vt example whose stated purpose is “Slice GeoJSON into vector tiles on the fly in the browser.” — [GeoJSON API](https://openlayers.org/en/v10.1.0/apidoc/module-ol_format_GeoJSON-GeoJSON.html), [geojson-vt example](https://openlayers.org/en/latest/examples/geojson-vt.html)
- MapLibre 6.13.0 depends on `@maplibre/geojson-vt`, so GeoJSON sources are tiled in a worker rather than drawn as one path per feature. — [unpkg package.json](https://unpkg.com/maplibre-gl@6.13.0/package.json)
- deck.gl’s project text claims “Performant rendering and updating of large data sets” and picking, without a polygon-count threshold. A Google Maps sample uses deck.gl GeoJsonLayer for “thousands of points,” which is points, not polygons. — [yarn mirror of the deck.gl readme](https://classic.yarnpkg.com/en/package/@deck.gl/geo-layers), [Google Maps deck.gl example](https://developers.google.com/maps/documentation/javascript/examples/deckgl-points)
- A 2024 Medium post reports one author’s Leaflet GeoJSON render at about 20 seconds average versus MapLibre on that author’s (unspecified-size) dataset, and attributes the difference to Canvas versus WebGL. The feature count and hardware are not in the excerpt. This is a single anecdote, not the 2025 controlled study. — [Medium, 2024-05-05](https://medium.com/@dipakpatil2615/rendering-hundreds-of-thousands-of-polygons-using-js-because-gis-deserves-modern-visualization-e27d678dccca)
- A react-leaflet issue from 2021 says ~40,000 GeoJSON features in canvas mode took ~30 seconds to first render with react-leaflet and a few seconds with Leaflet’s own GeoJSON layer. Old, and the bottleneck was the React binding as much as Leaflet. — [react-leaflet issue 865](https://github.com/PaulLeCam/react-leaflet/issues/865)
- A Tencent Cloud write-up of an informal point test (not polygons) claims SVG markers bog down around 3,000–5,000 points and Canvas still handles tens of thousands. Not a polygon result and not an official Leaflet number. — [Tencent Cloud article](https://cloud.tencent.com/developer/article/2693715)

### Inferences
- “Stalls” is the wrong shape for the 2025 data. At 10,000 polygons the canvas libraries won on initial render. At 50,000 polygons the faster three were still near 1.3–1.5 s. A world country layer is about 200–250 polygons and would not be the expensive part next to municipalities.
- 5,570 Brazilian municipalities are inside the paper’s “up to 10,000 polygons” band only if each feature is about as heavy as the OSM polygons they used. Municipal boundaries are often much denser in vertices. The paper does not separate feature count from vertex count, so it does not certify a 5,570-municipality choropleth.
- If the GISCarta version pin is accurate, the MapLibre result is for 4.7.1, not 6.13.0. Treating MapLibre as “slower at polygons” in 2026 without a new run would over-read the paper.
- D3’s usual output is one SVG element per feature. That cost model is not in the 2025 study. No sourced stall threshold for D3 SVG or D3 canvas was found. deck.gl and Cesium were not in the study either; both are GPU engines aimed at larger scenes, but no polygon stall number was published in the pages read.
- The practical levers the docs do name, short of a stall count, are Leaflet’s canvas versus SVG choice (not confirmed in the paper’s methods excerpt), OpenLayers `RenderFeature` and geojson-vt, and MapLibre’s worker-side geojson-vt.

### Gaps
- No stall threshold (frame time, main-thread block, or “unusable pan”) for any engine.
- No 2025–2026 benchmark of D3 SVG, D3 canvas, deck.gl GeoJsonLayer, or Cesium GeoJsonDataSource at 5,000–50,000 polygons.
- The IJGI paper’s methods excerpt retrieved here does not say whether Leaflet was SVG or `preferCanvas`, nor the CPU/GPU of the test machine, nor vertex totals.
- SD figures conflict between the MDPI PDF and the ICA abstract. Means match; do not treat the standard deviations as settled.
- No measurement on the IBGE municipal mesh plus a world layer together.
- MapLibre 6.x and OpenLayers 10.11 were not the builds in the 2025 study (10.2.1 and 4.7.1 are claimed only by the secondary blog).

## What is the smallest way to embed each library in a single self-contained HTML file?

### Takeaway
The smallest official embed for Leaflet, D3, OpenLayers’ prebuild, and deck.gl is one HTML file with one or two CDN script/link tags and no build step. MapLibre 6.13.0 is ESM-only on the CDN (`maplibre-gl.mjs` plus CSS) and also fetches a worker. Cesium’s documented download is a 128 MB zip; the combined `Cesium.js` is already 1.77 MB gzip and is not the whole runtime. Mapbox is a single UMD script plus CSS, but it is not free/share. Gzip sizes below are `gzip -9` of the unpkg file on 2026-10-08.

### Cited Findings
- Leaflet 1.9.4 `dist/leaflet.js`: 147,552 bytes raw, 42,434 bytes gzip. `dist/leaflet.css`: 14,806 raw, 3,522 gzip. URLs: `https://unpkg.com/leaflet@1.9.4/dist/leaflet.js` and `.../leaflet.css`. The readme’s own figure is “about 39 KB of gzipped JS plus 4 KB of gzipped CSS.” — measured from [unpkg leaflet.js](https://unpkg.com/leaflet@1.9.4/dist/leaflet.js) and [unpkg leaflet.css](https://unpkg.com/leaflet@1.9.4/dist/leaflet.css); claim in [Leaflet readme mirror](https://www.webcomponents.org/element/leaflet)
- Those two files have no worker. Inlining them into one HTML, or referencing them with a script tag and a link tag, is the whole library. The 1.9.4 API is the global `L` line; the live tutorial’s `new GeoJSON` may be the v2 alpha instead (see the gap in the previous section).
- MapLibre 6.13.0 `dist/maplibre-gl.mjs`: 1,079,357 raw, 285,316 gzip. `dist/maplibre-gl.css`: 83,290 raw, 10,485 gzip. `dist/maplibre-gl-worker.mjs`: 508,314 raw, 143,724 gzip. There is no `dist/maplibre-gl.js` (404). — [unpkg dist listing](https://unpkg.com/maplibre-gl@6.13.0/dist/?meta), bytes measured from those URLs
- Official smallest HTML is a stylesheet link plus `<script type="module"> import * as maplibregl from 'https://unpkg.com/maplibre-gl@^6.13.0/dist/maplibre-gl.mjs'`. The docs say the worker is then loaded from that module URL via a blob URL, including from a cross-origin CDN. npm alternative: `npm install maplibre-gl` and `import {Map} from 'maplibre-gl'`. — [MapLibre docs](https://www.maplibre.org/maplibre-gl-js/docs/), [npm readme](https://npmjs.com/package/maplibre-gl)
- OpenLayers `ol@10.11.0/dist/ol.js`: 1,070,771 raw, 297,882 gzip, and it is a global `var ol=...` script. `ol.css`: 6,343 raw, 1,466 gzip. — [unpkg ol.js](https://unpkg.com/ol@10.11.0/dist/ol.js), [unpkg ol.css](https://unpkg.com/ol@10.11.0/ol.css)
- OpenLayers’ current examples are ESM imports (`import Map from 'ol/Map.js'`) built with Vite, not the fat `ol.js`. The WebGL example’s package.json is `"ol": "10.7.0"` plus Vite. So the 298 KB gzip file is the prebuilt global bundle; a tree-shaken choropleth import was not measured and would be a build step, not a single static tag. — [WebGL vector example](https://openlayers.org/en/latest/examples/webgl-vector-layer.html)
- D3 7.9.0 `dist/d3.min.js`: 279,706 raw, 92,459 gzip. `topojson-client@3.1.0/dist/topojson-client.min.js`: 7,169 raw, 2,605 gzip. A smaller choropleth subset, measured separately: `d3-geo@3.1.1/dist/d3-geo.min.js` 36,329 raw / 13,069 gzip; `d3-selection@3.0.0/dist/d3-selection.min.js` 13,522 / 4,279; `d3-scale@4.0.2/dist/d3-scale.min.js` 15,728 / 4,874. — those unpkg URLs
- deck.gl 9.4.0 `dist.min.js` (the file named in package.json `"files"`): 2,073,497 raw, 574,961 gzip. Docs tell you to use `<script src="https://unpkg.com/deck.gl@^9.0.0/dist.min.js"></script>` or `npm install deck.gl`. No stylesheet is required for a canvas-only deck. — [unpkg deck.gl@9.4.0/dist.min.js](https://unpkg.com/deck.gl@9.4.0/dist.min.js), [GeoJsonLayer installation](https://deck.gl/docs/api-reference/layers/geojson-layer)
- Cesium downloads: “Download CesiumJS 1.146 128 MB” on 2026-10-01, or `npm install cesium`. The combined browser file `Build/Cesium/Cesium.js` on unpkg is 6,080,574 raw, 1,773,186 gzip. npm unpacked size of the `cesium@1.146.0` package is 79,655,977 bytes. — [Cesium downloads](https://cesium.com/downloads/), [unpkg Cesium.js](https://unpkg.com/cesium@1.146.0/Build/Cesium/Cesium.js), [npm registry `cesium`](https://registry.npmjs.org/cesium)
- mapbox-gl 3.32.0 `dist/mapbox-gl.js`: 1,897,230 raw, 516,487 gzip. `dist/mapbox-gl.css`: 48,946 raw, 5,750 gzip. package.json `main` is `dist/mapbox-gl.js`. This is a single UMD script, but the license is the Mapbox TOS, not an OSI license. — [unpkg mapbox-gl.js](https://unpkg.com/mapbox-gl@3.32.0/dist/mapbox-gl.js), [package.json](https://unpkg.com/mapbox-gl@3.32.0/package.json)
- Mapbox’s transpiling guide (page dated 2026-03-17) says that from version 2 the library is an ES6 bundle and that transpiling the Web Worker separately “significantly increas[es] the bundle size.” — [Mapbox transpiling guide](https://docs.mapbox.com/mapbox-gl-js/guides/transpiling/)

### Inferences
- Truly one file and no extra network requests, by inlining: Leaflet (JS+CSS, ~46 KB gzip together), D3 (either the 92 KB full build or the ~25 KB geo+selection+scale+topojson-client sum, which is arithmetic of separate files, not one published bundle), OpenLayers `ol.js`+`ol.css` (~299 KB gzip), deck.gl `dist.min.js` (~575 KB gzip). MapLibre’s module-URL worker detection means a CDN module script is supported, but pasting `maplibre-gl.mjs` into a blob HTML without a worker URL was not shown in the docs and may not resolve the worker. Cesium is a directory of workers and assets (128 MB zip), not a one-file paste.
- “Self-contained HTML” that still uses a CDN is one file of markup for all of them except Cesium’s asset base. MapLibre’s one HTML file still causes a second fetch for the worker. Cesium needs `Cesium.js` plus the rest of `Build/Cesium` (widgets CSS, workers, assets); the base-URL setting was not re-read, but the zip size shows the distribution is not the 1.77 MB gzip script alone.
- The Leaflet readme’s 39 KB and this note’s 42,434-byte gzip differ by compression settings or by what was included. Both describe the same 1.9.4 `dist/leaflet.js` era. Prefer the measured 42,434 for the exact unpkg file, and keep “about 39 KB” as the project’s own claim.

### Gaps
- No tree-shaken bundle size was built for OpenLayers, deck.gl (core+layers only), or MapLibre. The figures are the published full dist files, which overstate a careful import.
- `d3-zoom` and `d3-scale-chromatic` sizes were not measured. A usable D3 choropleth often needs both, so the ~25 KB component sum is not a complete UI.
- Whether inlining `maplibre-gl.mjs` without a hosted worker URL works via an explicit worker option was not tested.
- The Cesium docs page for `CESIUM_BASE_URL` / widgets.css was not opened. Only the zip size, the `Cesium.js` byte size, and the npm unpacked size are measured.
- Leaflet 2.0.0-alpha.1 bundle size was not measured.

## Which ones are actively released in 2025 or 2026?

### Takeaway
As of 2026-10-08, MapLibre, OpenLayers, deck.gl, CesiumJS, and Mapbox GL JS all have a stable npm release in 2026. Leaflet’s stable release is still 1.9.4 from 2023-05-18, with a 2.0 alpha and commits into 2026. D3 and d3-geo were last published 2024-03-12. topojson-client 3.1.0 dates from 2019-11-06 and should be treated as stale. ECharts 6.1.0 (2026-05-19, Apache-2.0) and maptalks 1.12.1 (2026-02-10, BSD-3-Clause) are additional live OSI projects, not fully profiled.

### Inferences
- For a project that wants a maintained free/share map engine in 2026, the libraries with a stable release in calendar 2026 are MapLibre GL JS, OpenLayers, deck.gl, and CesiumJS. Mapbox GL JS is also on a 2026 release train but fails the license test.
- Leaflet is maintained (2026 commits, a 2.0 alpha announced in 2025 and still alpha in September 2026) but the installable stable artifact is from May 2023. Calling “Leaflet” actively released in 2025–2026 is true of the repo and false of the `latest` tag.
- D3 7.9.0 is not older than 2024, so it is not in the “possibly stale” bucket by the 2024 cutoff, but it had no 2025 or 2026 release. topojson-client is the stale one: last release November 2019. It is still the published converter those D3 maps use; “no release” here means no new version, not that the TopoJSON format broke.
- ECharts and maptalks are real 2026 OSI options if the report needs another name. They were not checked for CDN size, GeoJSON API, tile-less choropleth, or polygon performance in this pass. Kepler.gl was not treated as a separate engine because the deck.gl docs present it as an application on top of deck.gl, and that relationship was not re-verified on a Kepler page.

### Gaps
- Leaflet 2.0.0-alpha.1’s exact npm publish timestamp was not printed. The 2025-05-18 blog URL was cited by the FOSS4G deck and not opened.
- Commit-level maintenance for D3 after March 2024 (commits without a release) was not checked. Only the npm `latest` time is known.
- ECharts `registerMap` / geo choropleth behavior, maptalks’ renderer, and both libraries’ bundle sizes and TopoJSON support were not researched.
- No source established a security-support commitment (CVE response) for any of these projects; “actively released” here means a version was published, not that a support window was promised.
